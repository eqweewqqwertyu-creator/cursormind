一、结论速览

DeepSeek Harness（官方 CLI 命令 dsh，npm 包 @deepseek-ai/dsh，MIT 协议）已作为灵标的执行引擎接入，替换此前借用的 heyClicky codex.exe 通道。接入方式为子进程 spawn：dsh headless profile 一次性应答任务，NDJSON 事件流实时映射到灵标气泡、回复面板与托盘忙态。CLI 双实验与 Electron 主进程端到端实测全部通过，单任务成本约一分钱。

二、背景与决策

2.1 为什么要换引擎

  • 卸载依赖风险：旧通道借用的 codex.exe 位于 heyClicky 安装目录（C:\Users\...\HeyClickyApp\current\CodexRuntime\bin），heyClicky 一旦卸载或升级换目录，灵标执行引擎即断链。
  • 协议适配成本：codex-cli 0.152.1 已删除 chat wire_api，只支持 Responses API；DeepSeek V4-Flash 虽已原生适配，但 codex.exe 是为 OpenAI 生态设计的通用 CLI，模型元数据告警（Model metadata not found）持续存在。
  • 厂商一致性：dsh 是 DeepSeek 自家出品的官方 harness，「框架 + 模型 + API」同厂同源，未来演进（缓存、计费、工具协议）优先保障。
  • 工程正当性：heyClicky 的核心架构正是「嵌入开源 harness 当执行引擎」；灵标直接采用官方开源 harness，路径一致且完全合规（MIT 协议，无反编译、无内部配置泄露）。

2.2 dsh 是什么

DeepSeek Harness 是 DeepSeek AI 于 2026 年 8 月 13 日与 V4 Pro 同日开源的 Agent 运行框架，采用「一切皆插件」（everything-is-a-plugin）架构，由 Cordis 微内核驱动——模型、工具、沙箱策略、多 Agent 协调、会话存储均以插件形式挂载。CLI 命令为 dsh，提供四种运行形态：Web UI（默认 http://127.0.0.1:3080）、桌面端（Electron）、TUI 终端、headless 无头模式。灵标采用的是 headless 模式：答案上 stdout、诊断上 stderr、--json 输出机器可读事件流，天然适配子进程集成。

包名验证中的陷阱：npm 上的 dsh（1.0.1）是第三方 JavaScript shell 工具（infusion/node-dsh），deepseek-harness（0.0.1）是占位包。官方包是带 scope 的 @deepseek-ai/dsh，安装前务必核对 repository 字段。

三、实测验证

3.1 CLI 直测（两级实验）

  1. 实验一：建文件 + 读回确认

    任务「创建 dsh-test.txt，内容写 dsh引擎验证OK，然后读取确认」。引擎自主执行 write → read 两步，最终回复「已创建...读取确认内容为 dsh引擎验证OK，与要求一致」。总用量 6605 tokens（含缓存命中 6400）。

  2. 实验二：写代码 + 执行验证（能力上限探测）

    任务「创建 fib.js 实现 fibonacci，用 node 执行打印 fib(10)」。引擎先 glob 查重，发现昨日 codex 测试遗留的 fib.js 且实现正确，直接复用，调用 pwsh 工具执行 node .\fib.js，终端输出 55。shell 执行能力确认，headless 并非只读沙盒。总用量 6938 tokens。

  3. 实验三：Electron 主进程端到端

    灵标带 CURSORMIND_DSH_TEST 自检钩子启动，3 秒后自动派发真实任务。hotkey.log 完整记录事件链：启动 → session → 执行:写文件 dsh-demo.txt → 执行:读 dsh-demo.txt → final → turn 完成 in=1015 out=228。桌面「灵标工作区」产出 dsh-demo.txt（29 字节，UTF-8 内容逐字正确）。

四、接入实现

4.1 架构分工（双引擎）

agent.ts · 视觉教学引擎

「教我怎么用」：截图 + Qwen3-VL locate + 精灵指路，人在回路。毫秒级交互，短上下文，qwen-plus/DeepSeek 单轮调用。

dshRunner.ts · 执行交付引擎

「帮我干」：dsh headless 自主建文件、写代码、跑命令，工具循环与纠错全部由 harness 承担，灵标只收事件流与交付物。

4.2 调用形态与关键设计

# 灵标主进程实际派发的命令形态
cmd /c npx -y @deepseek-ai/dsh --profile headless --json -
# 任务文本经 stdin 喂入（dsh 以 "-" 读 stdin），规避命令行中文与引号转义问题
# env: 继承进程环境（DEEPSEEK_API_KEY 已由 .env 注入）
# cwd: 桌面\灵标工作区（交付物用户直接可见）
  • stdin 传任务：dsh headless 支持 - 从标准输入读取任务文本，中文与特殊字符零转义损耗。
  • cmd /c 中转：Windows 上 npx 是 .cmd 脚本，Node 20+ 出于安全禁止直接 spawn .cmd，经 cmd.exe 中转是标准做法。
  • 树式终止：cmd→node→dsh 是三层进程树，取消任务（Esc / 新对话）用 taskkill /T /F 杀全树，防孤儿进程。
  • 硬超时：默认 180 秒（CURSORMIND_DSH_TIMEOUT_MS 可调），harness 卡死不拖垮精灵。
  • 单任务模型：generation 计数器 + killTree，与 agent.ts 同构，新一轮自动取消上一轮。
  • 朗读净化：语音朗读前剥离 markdown 代码围栏，避免代码块被逐字读出。

4.3 意图路由

routeVoice 五层路由前置新增工作任务分流：正则命中「写/创建/生成/整理 + 文件/脚本/代码/文档」类动词宾语且不含「教我/怎么」教学词，即走 dsh 通道；教学类请求仍走视觉引导引擎，两类体验互不干扰。

六、风险与后续

  • 开发者预览版：官方明示「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」。升级前需回归 headless 事件流格式；建议锁版本（npx -y @deepseek-ai/dsh@x.y.z）。
  • npx 启动开销：每次任务经 npx 解析，冷启动约 2-5 秒。优化路径：npm i 将包固化为项目依赖，直接调 node_modules 内 bin；或预热常驻 dsh 守护进程。
  • DSH_HOME 隔离：当前使用默认配置目录，会话与凭据与用户其他 dsh 使用场景共享。后续可设 DSH_HOME 到 app userData 实现灵标专属隔离。
  • 安全边界：headless 可执行任意 pwsh 命令（实测已确认）。当前靠工作目录收敛 + 意图白名单约束；正式发布前应叠加任务级风险提示（删除/外发类命令先确认）。
  • 待提交：dshRunner.ts + index.ts 路由改动尚未入 git，与球缩小、开关链路等改动一起待真人语音实测后统一提交推送。
